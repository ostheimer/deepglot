# AI budget governance (#319)

## Units and approval

Plan word quotas, platform credits, subscription charges, and external provider charges are separate. This feature does not purchase credits, upgrade a plan, or charge a subscription. There is no implicit included AI credit allowance. An organization OWNER must approve both scopes independently; project admins can read the status but cannot approve spending. **Enforcement is inactive by default.** While inactive, the policies can be prepared and read back, but current provider calls follow the pre-existing translation path and are neither blocked by these policies nor recorded in this spend ledger. When enforcement is explicitly activated, a missing organization or project policy denies fresh provider work, including legacy tenants and the mock provider. There is no per-tenant legacy exception or automatic budget synthesis.

Money uses integer micros of the chosen ISO currency (one currency unit = 1,000,000 micros). An owner enters conservative *maximum* input and output charges per million provider units, a per-call cap, a monthly cap, a warning percentage, and a price expiry for each exact provider/model pair. For example, USD 0.25 per million input tokens is `250000` micros per million. This is an owner assertion and snapshot, **not a claim about a provider's current tariff**. The organization and project policies must use the same currency, UTC monthly period, provider/model pair, and unit. No FX conversion is inferred. The price snapshot expires within 90 days and must be renewed explicitly. Unknown/stale/mismatched approvals deny dispatch.

OpenAI-compatible and Gemini adapters use provider token usage. Gemini's measured output includes both candidate and thinking tokens; a malformed or inconsistent total retains the hold. [Google's token guide](https://ai.google.dev/gemini-api/docs/generate-content/tokens) documents these separate counts. The DeepL adapter requests `show_billed_characters=true` and sums only integer `billed_characters` receipts from every translation; absent or malformed receipts remain `UNKNOWN` at the full hold. Output characters are not billed by this policy. [DeepL's OpenAPI contract](https://github.com/DeepL/openapi/blob/main/openapi.yaml) defines this response field. Mock has a zero-cost receipt. A separately approved local Ollama model can have zero provider charge, though its infrastructure cost is outside this meter. Exact provider/model identifiers are required; a fallback must have its own approval in both scopes. Other gateway tariffs are not guessed. OpenRouter, OpenAI-compatible gateways, and billed Ollama endpoints also require an explicit per-model owner attestation that their output-token cap is enforced; without it, dispatch is blocked. A planned AI media action is not enabled by this policy.

## Preflight and dispatch

`POST /api/projects/{projectId}/ai-budget` is a read-only estimate. It accepts an action (`TRANSLATION`, `CONTEXT_TRANSLATION`, `BULK_TRANSLATION`, `AI_EDIT`, `REWRITE`, `IMPROVE`), exact provider/model and bounded input/output unit counts. It returns the currency, ceiling, remaining headroom, period, and whether the action touches external provider cost. While enforcement is inactive, it marks the result `previewOnly`, reports `allowed: null` and exposes only `wouldBeAllowedIfActivated`; it does not imply an active hard cap. A preflight never reserves funds and does not approve a later dispatch. Its caller must include all prompt, context and framing units; the server-side dispatcher does its own conservative bound.

At each translation provider attempt, including fallback and count-mismatch isolation, the dispatcher validates credentials, locks Organization then Project, checks their current relationship and both approvals, and inserts a durable `DISPATCHED` reservation before HTTP. An input token bound uses UTF-8 bytes of the complete dispatch input plus 4096 bytes for adapter framing. Output tokens are capped in the OpenAI-compatible/Gemini request. DeepL reserves the approved character bound. A request group and dispatch instance prevent a stale idempotency lease from repeating provider work. The lock serializes cross-project reservations against the organization cap.

A complete trusted provider **unit** receipt replaces the hold with a reconciled **cost ceiling** using the immutable owner-approved maximum rates stored on the reservation. This is not an authoritative provider invoice or actual monetary charge. Missing, malformed, out-of-bound, interrupted, or failed receipts retain the full hold as `UNKNOWN`; they do not get an optimistic refund. Repeated settlement is idempotent. Reconciliation records provider, model, action, project, organization, actor ID or API key ID, estimated and measured units, reserved and reconciled ceiling, UTC period, and dispatch/settlement timestamps. It stores no credentials, prompts, source text, translated text, URLs, or end-user identity. A provider invoice adjustment or refund requires an independently verified manual reconciliation; no automatic refund is inferred from a failed HTTP call.

Automatic settlement re-reads the reservation after the Organization→Project lock and changes only `DISPATCHED` with a state compare-and-set. The first complete or unknown outcome is final for automatic retries; later conflicting receipts return that existing outcome without releasing more headroom. Budget admission and readbacks always count `DISPATCHED` and `UNKNOWN` at the full reserved ceiling, even if an older inconsistent row carries a stale reduced ceiling.

An OWNER can resolve a completed `UNKNOWN` hold through the dashboard or `PATCH /api/projects/{projectId}/ai-budget` only after independently checking a provider usage receipt or no-charge/credit statement. The input is an opaque receipt reference and, for usage, integer provider units. The server stores only a SHA-256 reference hash, reuses the original organization/project and immutable rate snapshots, writes a separate manual audit event, and rejects units above the original hold. Resolution uses a state compare-and-set: concurrent retries with identical evidence return the same result and create one event; conflicting evidence fails. A no-charge credit sets the monetary ceiling to zero without inventing measured token units. A `DISPATCHED` reservation cannot be released through this path: it may still represent in-flight provider work and requires separate operator investigation. The owner assertion is not a claim that the application independently verified an invoice.

The period is the UTC calendar month, with no rollover. A reservation remains in the month of dispatch even if the provider responds after midnight. Old unsettled rows remain visible and do not free money in their dispatch month. Warning and exact-cap crossings create idempotent, tenant-scoped events. The current organization's OWNER and ADMIN members receive these as localized, permission-checked dashboard alerts with the current reserved/reconciled ceiling and cap readback; project managers can also inspect their project's event list on its budget page. This is an in-app readback, not an email claim. The existing #268 preference/delivery contract supports optional scheduled email categories only and has no budget producer, so it is not used to imply mail delivery. Approval changes create separate durable audit events; general activity audit remains #266.

Project deletion and spend retention are intentionally separate. A project manager can delete a project only after all of its provider reservations are `SETTLED`. `DISPATCHED` and `UNKNOWN` block deletion with a localized link to the budget review; the decision is made under the same Organization→Project locks as admission and settlement. The project-content cascade removes translations, keys, settings and its project budget, but the sparse spend ledger retains the immutable original `projectId`, `organizationId`, UTC period, action, units and rate snapshot without a live Project foreign key. Settled charges therefore continue to consume the original organization's cap, including when a project is later transferred or deleted. These opaque IDs and monetary records contain no prompt, translated text, URL or credential. Current retention is until workspace deletion; there is no automatic time-based purge or claim of a statutory invoice retention period. Workspace deletion still cascades the ledger, and any shorter operational retention policy needs a separately reviewed erasure process that preserves active hard-cap periods.

## Rollout gate and existing customers

Apply `scripts/sql/ai-budget-governance.sql` before deploying code that reads these tables. The SQL is idempotent: it creates the new tables and drops only the unsafe `AiSpendReservation_projectId_fkey` cascade from any earlier version of this feature. Run it twice in an isolated clone and read back tables, indexes, constraints, preserved ledger rows, and zero unexpected approvals. Deploy the policy setup with `AI_BUDGET_ENFORCEMENT` absent or explicitly `off`. `GET /api/projects/{projectId}/ai-budget` must read back `enforcementState: inactive` and null committed totals; the dashboard must say that current provider calls are not limited or metered by these budgets. Independently verify OWNER and project-manager readbacks and the unaffected translation path with neutral local fixtures. Do not call a paid provider or change a customer budget as a smoke test.

`AI_BUDGET_ENFORCEMENT=on` is a later, separate server-side deployment decision. Invalid values fail configuration validation; there is no tenant override. Once active, every provider attempt in the integrated dispatchers must reserve under the full policy before HTTP, including fallback and retries, and API/UI readbacks show active limits and reserved/reconciled ceilings. Before activation, obtain the OWNER approvals for both scopes and exact current provider/fallback models, then verify the affected project count and activation window. Turning enforcement off again would stop *new* budget metering; previous reservations remain auditable but do not represent provider use during the inactive interval. Do not claim that the ledger is a complete provider bill across such intervals.

The activation consequence is material: the read-only production check at 2026-10-09 04:47 UTC found 11 projects with active automatic target languages in 2 organizations, no budget tables, and 5 projects in 1 organization with positive fresh external-provider translation batches during the preceding 30 days. One project explicitly used Gemini, one Mock, and nine had no explicit project provider; their effective environment fallback cannot be inferred from project settings. Translation batches count application-level fresh words, not provider token receipts or invoices. Activating enforcement without OWNER setup would make new uncached provider translations return `budget_unapproved`. Cached, manual, glossary, and other non-provider responses remain available. Prepare the policies first while enforcement remains off, then obtain an explicit customer activation-window decision. Do not synthesize budgets, auto-approve prices, or add a legacy bypass. Recheck #263 URL dispatch receipts, #267 transfer locks and BYOK reconnect, and #257 AI edit DISPATCHED state after those branches land. A transfer must stop while any project reservation is `DISPATCHED` or `UNKNOWN`; the original organization attribution and settlement must remain valid. None of these cross-branch gates may be inferred complete from this isolated implementation.
