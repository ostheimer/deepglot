On 2026-10-09 the source queue also ran in a disposable **real WordPress 7.1 / PHP 8.3 / MariaDB 11** Compose project (`deepglot257source`) with the worktree plugin mounted read-only, a minimal local theme and neutral published pages. A separate container served a local mock SaaS endpoint. The fixture used only a local synthetic key; no real provider, customer site, or shared database was contacted. A fully cached `/en/quelle-257/` returned HTTP 200 with translated title/body in about 0.03 seconds and made **zero** inventory HTTP calls. `wp cron event list` showed `deepglot_report_source_inventory`; `wp cron event run` sent only two expected source hashes with the original `capturedMicros` and drained the queue. Automatic WP-Cron spawning was disabled in this disposable fixture after event scheduling was verified, so subsequent failures could be driven deterministically through the real cron hook.

With mock 503, two cached page renders took 0.029 and 0.017 seconds and caused no inventory HTTP. The cron attempt left the digest payload pending with a 60-second retry timestamp and no success transient. A mock response delayed beyond the two-second client timeout blocked only the cron invocation (2.01 seconds); the next cached page still rendered in 0.029 seconds. A `?campaign=private-token` request, a `?preview=true` request and an authenticated WordPress frontend request each produced `complete=false`, empty hashes and a query-free URL context; the real cron subsequently sent the two distinct contexts with zero hashes. A capture older than five minutes, a changed API key and a changed API base URL were each dropped with zero additional mock HTTP calls. The mock log contained only source-inventory calls plus one unrelated runtime-config refresh after the fixture's five-minute configuration interval; it contained no translation/provider calls, source text or private query token.

The real concurrent test exposed a bug missed by the first PHP harness: a cron process waiting for mock HTTP retained its **request-local WordPress options cache**, so its successful old response deleted a newer observation written by another WordPress process. The observed RED state was an empty queue after the newer digest was visible in `wp_options`. The fix rereads the queue from persistent options under the short mutation lock after HTTP. The final GREEN run took 0.213 seconds for the cron action and left exactly the newer digest pending after the old response succeeded. `SourceInventoryAsyncTest.php` now models this stale request-local cache explicitly. The local Compose volumes, containers, synthetic pages, mock request log and temporary scripts are disposable fixtures and are removed after readback.

The lock lease itself was checked separately in disposable WordPress/MariaDB project `deepglot257lease`, using two independent PHP processes and direct `wp_options` readback. Process A acquired the ten-second queue lease and paused in its mutation; after eleven seconds process B reclaimed the expired lease. Before the fix, B's completed `winner=b_finish` queue was overwritten by A's stale `winner=a` write. In a second run, B held its new lease while A resumed, and A's cached `get_option` plus unconditional `delete_option` removed B's lock. With a locked owner comparison around the final WordPress option write and a conditional SQL owner delete, the same two runs kept `winner=b_finish` after A resumed and kept B's lock while B still held it; B then completed normally. A rejected stale commit also cannot create a success receipt for a queue removal. Focused PHP queue tests and PHP syntax validation passed. The fixture used only a synthetic local WordPress account and was removed with its database volume.
