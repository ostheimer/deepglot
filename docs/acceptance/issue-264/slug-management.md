# Issue 264: slug management acceptance

The direct editor from PR 374 remains the single-row path. This change adds source and target search, active-language and translated/untranslated filters, current-page selection, four-column CSV export of selected rows, and atomic reset of up to 25 selected rows. Only project managers can edit, reset, or import URL slugs. Language-bound translators can view and export only their assigned active language.

The existing `originalSlug,translatedSlug,langTo,urlCount` CSV format is unchanged. A direct edit appears in both full and selected exports, and that export can be reimported. The slug import now validates the complete prospective project map and writes all rows in one serializable transaction under the project configuration lock. It rejects reserved or colliding targets and normalized source aliases, returns the original CSV line and target for a conflict, and leaves no partial import. It preserves the 5,000-row import cap. A successful import also queues its row and completion webhook events in that transaction. Other import assets retain their existing chunked behavior.

The SaaS database reflects a successful edit, reset, bulk reset, or import immediately. The WordPress plugin fetches runtime configuration when a request finds its 300-second refresh interval due, or when settings sync is forced. Applying that payload replaces the dedicated URL-slug option and invalidates the WordPress options cache. This is the routing-cache update boundary; an upstream/full-page cache on a customer site can require a separate clear. An inactive site makes no request and therefore has no elapsed-time guarantee for applying a new map.

After sync, a source URL and links generated from it use the new translated target as canonical. A stale source-language segment on a target-language route receives the existing one-hop 301 redirect for safe GET/HEAD requests after WordPress resolves the source. An *old translated target* has no redirect history: it is no longer reverse-mapped and follows normal WordPress routing, often a 404. No automatic redirect from an old translated target is promised. Queries remain intact. WordPress infrastructure/media segments bypass slug translation; numeric content segments remain eligible.

Local evidence: Node 24 typecheck, unit regressions, PHP/WordPress suite, and six Playwright scenarios passed with dedicated PostgreSQL and mock provider. Browser cases cover manager edit/reset and CSV roundtrip, translator write denial and language isolation, search/status filters and selected bulk reset, stale bulk CAS with rollback, CSV line conflict with no write, 101-row cross-boundary mapping move, and simultaneous collision claims. `RequestRouterSlugTest.php` now exercises changed-map canonical links, old-target behavior, media bypass, and numeric segments. The browser fixture was disposed after testing; no customer slug was changed.

Upper-bound local fixture: 5,000 valid CSV rows with one subscribed webhook endpoint imported in 490 ms. An idempotent reimport took 455 ms; readback retained exactly 5,000 IDs and queued 10,000 `slug.upserted` deliveries across both imports. Fixture slugs and the endpoint read back as zero after cleanup, and the isolated PostgreSQL container was removed. These measurements describe the local fixture, not a production latency guarantee.
