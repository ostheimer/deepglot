# Issue 264: direct edit of an existing translated URL slug

Managers can edit or clear one existing mapping on the slug page. This slice does not add slug discovery, bulk actions, auto translation, or redirect history; Issue 264 stays open for that remaining scope. The existing four-column slug CSV import/export contract is unchanged. A direct edit appears in export, and the exported CSV can be reimported. CSV import retains its existing validation and overwrite behavior; the stricter collision checks apply to the new single-row edit endpoint.

The PATCH endpoint checks project management permission, row ownership, an active target language, and an `updatedAt` compare-and-swap inside a serializable transaction under the project configuration lock. A normalized target must be a single safe segment and must not collide with any source or translated segment in its language. It also must appear in the runtime URL slug payload. The existing source must itself be routable by the WordPress plugin; clearing a mapping remains possible even when the source is malformed. Language-bound translators can read only their active target language and have no edit control or PATCH permission.

A successful write is immediately stored in the SaaS database. The WordPress plugin fetches runtime configuration when a request finds its 300-second refresh interval due, or on a forced settings sync. On successful sync, its URL slug option and WordPress options caches are updated/invalidated. The current plugin does not prove an automatic full-page or upstream cache purge for slug edits; check and clear those caches separately on a customer site where needed. The newly configured translated path becomes the canonical target after sync. An old translated target receives no automatic redirect because this slice stores no redirect history.

Local verification used a dedicated PostgreSQL container, test login, mock translation provider, and disposable fixtures. The URL slug and runtime unit regressions, full unit suite under Node 24 (779 passed), PHP/WordPress plugin suite, typecheck, ESLint, and production build passed. Three Playwright scenarios passed together: manager edit/reset plus unchanged CSV roundtrip and stale-write rejection; language-bound translator read/write isolation; and simultaneous different-row claims on one target resulting in one HTTP 200, one HTTP 409, and one persisted owner. The UI had no horizontal overflow at 390 pixels. A Node 26-only pre-existing AsyncLocalStorage failure in `proxy-static-assets.test.ts` did not reproduce under Node 24. No customer or production slug was changed for verification.
