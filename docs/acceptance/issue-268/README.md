# Issue 268 notification preferences

The additive schema adds `NotificationPreference` and `NotificationDelivery` with workspace and recipient foreign keys. Apply the reviewed schema to each deployment target before running the new account page. The existing `OrganizationMember.activityDigestEnabled`, `ActivityDigestDelivery`, and mandatory mail paths are unchanged.

| Category | Frequency and role | Current producer / job |
| --- | --- | --- |
| Existing weekly activity digest | Weekly; each opted-in member sees their permitted projects | Existing `/api/cron/activity-digest` job, unchanged |
| Product updates | Off or monthly; current workspace members | None; persisted preference and dispatch contract only |
| Project notices | Off or weekly; current members with access to every referenced project | None; persisted preference and dispatch contract only |
| Billing summaries | Off or monthly; current owners/admins | None; persisted preference and dispatch contract only |
| Account and security notices | Mandatory, outside this preference API | Existing transactional flows, unchanged |

The new categories are off when no row exists. A member may edit only their own workspace preferences. Billing summaries require a current owner or admin role to opt in; anyone can turn a formerly enabled category off. A future category producer must aggregate events for one user/workspace/category/UTC period and use `dispatchOptionalNotification`; it rechecks membership, role, every represented project ID and its workspace, project membership, and the current preference immediately before sending. The unique claim key and pending-send sentinel prevent concurrent sends. An unsent stale claim can be reclaimed after 15 minutes. A positively rejected send may release the claim, while timeout or uncertain provider acceptance retains the sentinel and returns `unknown` until provider evidence resolves it. The original UTC period key must be retained for late jobs. This is duplicate suppression, not a guarantee of exactly-once delivery. No producer is installed, so no new category mail is currently sent.

The existing weekly digest adapter now distinguishes documented Cloudflare REST rejections from uncertain 500, malformed, and timeout responses. It marks a send as accepted only when [Cloudflare's recipient-grouped response](https://developers.cloudflare.com/email-service/api/send-emails/rest-api/) lists that recipient under `delivered` or `queued`. A permanent bounce remains terminal and is not marked sent or automatically retried. `queued` proves provider acceptance, not inbox delivery.

The account page fetches preferences with an independent GET and re-reads after PATCH. Turning a category off is its unsubscribe action. The weekly digest remains a separate opt-in; account and security email cannot be controlled from this route.
