# Automatic subscription upgrades (#269)

The feature is opt-in and owner-only. Deploying this code does not enable any organization. An owner must choose a maximum tier and a maximum recurring EUR price that covers every step through that tier, and explicitly acknowledge the immediate prorated invoice. The page shows the next tier, the recurring ceiling and a 12-month total for monthly billing or annual total for yearly billing; Stripe's actual immediate invoice may differ due to tax, credits and discounts. The existing monthly or yearly interval is preserved. Enterprise, Free, synthetic customers, trialing/past-due/canceled subscriptions, scheduled cancellations, subscription schedules, pending Stripe updates, multi-item subscriptions and unrecognized or mismatched prices are ineligible. No currency conversion occurs.

`POST /api/translate` is the installed producer. It invokes the upgrade evaluator only after a fresh translation and its measured monthly word usage are committed. The threshold is 90% of the current tier's monthly word limit. The evaluator requests exactly the next paid tier, with one durable attempt per organization, UTC usage month and starting tier. It retrieves the current Stripe subscription and both configured prices, checking active EUR fixed-unit prices, amount and billing interval. It then rereads the owner's preference, measured usage, organization plan and subscription under an organization row lock and commits a `DISPATCHING` claim. The paid Stripe request runs after that commit, with no database lock across network I/O. A changed preference or Stripe state before dispatch cancels the attempt. Disabling prevents future dispatch; an already dispatched Stripe request may still complete. The owner preference route takes the same organization lock.

The Stripe update replaces the one subscription item using `payment_behavior=pending_if_incomplete`, `proration_behavior=always_invoice` and the durable attempt ID as idempotency key. A lost response leaves the committed `DISPATCHING` claim in place. A later measured usage event or the protected 15-minute `/api/cron/auto-upgrade` scheduler can retry the same key after ten minutes only if the remote subscription still has the original price, has no pending update, and the request remains inside Stripe's 23-hour idempotency window. The scheduler is bounded to 20 unresolved attempts per run and never creates an attempt without measured usage. A changed remote state with no bound response is held as `UNKNOWN` for manual reconciliation; an older uncertain attempt is also held. Never create a new key merely because a response was lost. A pending payment or SCA request retains the old quota; the owner sees a payment-action notice and can use Stripe billing management. Expired pending updates become `EXPIRED` with a failed notice and no automatic second debit.

Stripe's paid invoice event (or subscription event backed by a retrieved paid invoice, including immediate post-dispatch reconciliation) is required to apply the target plan and quota. The invoice ID must first be bound from the response to this exact idempotent update. The reconciler checks paid status, billing reason, customer, subscription, latest invoice and an invoice line for the target price. It rereads the attempt and current local subscription under the organization lock, then writes entitlement, `APPLIED` and owner notices atomically. A delayed old renewal invoice cannot satisfy this proof; its payment failure still follows the normal past-due path. The existing subscription remains authoritative until paid proof. Attempted, payment-action, failed and applied notices are durable, unique per owner and attempt. Opt-in authorizes the organization, not just the owner who saved it; a later owner role change does not silently revoke the workspace preference. Revoked owners cannot read preference/history or receive new notices. If there is no current owner, dispatch is canceled. The plan overview GET is uncached and independently reads the persisted preference and last 20 attempts.

Before rollout, apply `scripts/sql/auto-upgrade.sql` to the verified target database using the repository's schema deployment procedure, then deploy code. The SQL is additive, repeatable and creates no enabled preference rows. Verify generated Prisma schema, all configured Stripe price IDs and webhooks in the target environment. Do not run a real paid upgrade as acceptance without an explicit customer fixture and authorization. Local acceptance uses a disposable PostgreSQL database and an injected fake Stripe contract. If an attempt is `CLAIMED` with `UNKNOWN_EXTERNAL_OUTCOME` beyond 23 hours, inspect Stripe subscription, pending update and latest invoice first; reconcile the attempt and entitlement from a paid invoice. Do not replay an expired idempotency key.

Relevant Stripe documentation: [pending updates](https://docs.stripe.com/billing/subscriptions/pending-updates), [changing a subscription price](https://docs.stripe.com/billing/subscriptions/change-price), [idempotent requests](https://docs.stripe.com/api/idempotent_requests).
