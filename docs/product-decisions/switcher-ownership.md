# Language switcher ownership and synchronization (v1)

The WordPress plugin remains the source of truth for every existing project. A new plugin reports a complete switcher snapshot through `POST /api/plugin/settings-sync`: the default switcher and all named instances, including style, labels, language order, custom names and flags, CSS, responsive settings, and placement selector. Older plugins omit the field; their normal project settings sync remains compatible, while the dashboard requires a v1 snapshot before it offers adoption.

A project manager may explicitly adopt the last reported snapshot in the dashboard. The first save includes the snapshot timestamp and the current dashboard revision. The SaaS transaction checks both under the project lock. The stored v1 configuration and revision then become authoritative. `GET /api/plugin/runtime-config` sends the v1 owner, revision, configuration, and the WordPress snapshot on which adoption was based. The plugin compares that base with its current switcher settings before applying anything. A local edit after the snapshot leaves the WordPress configuration intact and raises a visible conflict. Later revisions apply only while local settings still match the previously applied configuration. The plugin acknowledges an applied revision in its next settings sync. The dashboard shows pending revisions, old mirrors, and conflicts.

WordPress settings remain editable during SaaS ownership. Such an edit is preserved and reported as a conflict; the manager can inspect it in WordPress and return control there. Returning control is an explicit dashboard action with the same revision check. The SaaS then sends `owner: wordpress` with a newer revision, which clears the plugin's applied-revision marker without changing any switcher setting. The plugin retains a monotone last-seen revision, so a delayed earlier SaaS or WordPress response cannot reverse the owner. A later dashboard adoption starts from a new WordPress snapshot and a still newer revision.

The contract is additive. An old plugin sees no legacy switcher fields in the new runtime payload, so it does not change its existing switcher options. A new plugin connected to a WordPress-owned project receives only the ownership marker and does not replace settings. Unrecognized or mismatched runtime configurations fail closed in the plugin. Normal settings sync still records the origin site; a foreign installation cannot become the source of a switcher snapshot.

The JSON contract version is independent of the WordPress plugin version. TypeScript and PHP share canonical SHA-256 fixture values for Unicode names, custom flags, empty maps, and differing object-key order. Array order stays significant. Schema changes require a new contract version and compatibility tests before either side emits it.

Acceptance on customer sites is read-only. Use a disposable WordPress/database fixture to exercise adoption, runtime application, local edit conflict, ownership return, and cleanup. A SaaS deployment alone does not establish that a customer WordPress installation has received the new plugin version.
