# Workspace ownership and project transfer (#267)

An `Organization` is the persistent SaaS workspace. Owners and admins can rename it; an account can create another Free workspace up to the highest explicit `workspacesLimit` of an active/trialing workspace it owns (Free: one). Each workspace also has an explicit `membersLimit` (Free: one; Starter: three; Business: five; Pro: ten; Advanced: 25; Extended: 50; Enterprise: 100). An inactive or missing subscription uses Free limits for these operations. This does not create or modify a Stripe customer. New Free workspace subscriptions use a synthetic `free_workspace_` identifier and must pass `isRealStripeCustomerId()` before any later Stripe Customer API call. Projects are created into an explicit managed workspace.

Workspace administration is limited to registered people already visible in another workspace the actor manages. There is no global email search or account enumeration. Owners can add a known user as MEMBER or ADMIN, change roles including promotion to OWNER, and remove members except the last OWNER. Admins can add or remove MEMBER only, cannot edit roles, and cannot elevate themselves. Current roles and seat count are rechecked under the workspace row lock in the same transaction as the mutation and `WorkspaceAudit` receipt. Removing a member also revokes their project roles and pending project invitations in that workspace, unassigns their translations through the existing relation, and cascades that membership's optional notification preferences and delivery claims; no email is sent. Inviting an unknown person remains unsupported.

Billing checkout, cancellation, address updates and portal access use an explicit workspace selection when an account belongs to multiple workspaces. Immediately before any Stripe dispatch, the server takes the same workspace row lock as role changes, re-reads OWNER/ADMIN membership and issues a durable `BillingCommand` recording the actor, role, action and selected price/customer/subscription reference. A role downgrade committed before issuance denies the call. A downgrade after issuance does not retroactively revoke the already-authorized external request. The lock is released before Stripe HTTP; the command records authorization, not a claimed Stripe outcome. Internal placeholder customer IDs remain excluded from Stripe Customer calls.

Transfer requires current server-side OWNER or ADMIN membership in **both** source and destination. Knowing a destination ID or a preview token never grants access. The source project and destination capacity are re-read in a serializable transaction. A five-minute signed preview binds the actor, project, destination, source state, project version, relevant child rows including URL provider and receipt state, destination membership and plan/usage. A changed state requires a fresh preview. A `TranslatedUrl.provider_pending` operation with an unresolved external outcome blocks both preview and commit under the Organization→Project lock; it must be reconciled before credentials are purged. An older receipt without evidenced originating workspace also blocks that project's preview and commit. The user must explicitly acknowledge the visible consequences before commit. One transaction performs revocation, move and a durable `ProjectTransferAudit` receipt. Failure rolls everything back; the receipt stores IDs, actor, version and fingerprint, never secrets or translated content. The audit is factual from this feature onward, with no invented backfill.

| Data | Transfer behavior |
| --- | --- |
| Organization members and roles | Remain with their respective workspace. No member is added to the destination. Source OWNER/ADMIN must also be destination OWNER/ADMIN. Project members survive only if their user is already a destination member; project ADMIN additionally requires destination OWNER/ADMIN. Others are removed and assigned translations become unassigned without losing text. Pending source invitations are revoked. |
| Subscription and billing owner | Both organization subscriptions stay in place. Stripe is not called and no customer or plan is moved. Destination project and language caps and available monthly quota are validated. |
| Usage, batches and URL receipts | Existing `UsageRecord` and `TranslationBatchLog` rows retain their original `organizationId`, including the current month. New writers capture `UrlOperationReceipt.originatingOrganizationId` atomically with billed usage and it never changes on transfer. A legacy NULL receipt is not attributed by guesswork and blocks that project's transfer until original billing evidence resolves it. Old receipt recovery and idempotency are scoped to the originating workspace, so the destination cannot replay the source receipt. These records are neither reattributed nor billed twice. Future successful requests use the destination workspace. In-flight usage/batch writes verify and hold the current project workspace row, so a request that read the old owner cannot write old attribution after transfer. WordPress-local caches are not retroactive SaaS usage. |
| Translations | All translations, manual edits, content revisions, metadata, type/context observations, glossary and exclusions stay with the project. Source-only assignment IDs are cleared by the existing `SetNull` relation. No provider call runs during transfer. |
| URLs, slugs and media | Translated URLs, URL slugs, domain mappings, media replacements, digest-only `UrlCacheInvalidation` rows/cursors and page-view rows remain project-scoped. No old plugin credential can read the cursor after transfer; a new destination key establishes its own runtime connection. Public URLs may need site-side verification after reconnect. `provider_pending` URL operations block transfer until reconciled. |
| Plugin API keys | Hashed keys cannot be recovered or re-encrypted. All existing keys are deactivated. The destination admin creates a new key through the existing explicit key flow and reconnects WordPress; transfer itself creates no key. |
| Provider key and runtime | The project provider key uses app-level AES-GCM, not organization-bound encryption. A source BYOK is cleared and `providerReconnectRequired` blocks fresh provider work, including fallback to a server-wide provider key, until a destination manager saves a new project key. A subsequent transfer preserves this pause even when the source key has already been cleared. The preview shows key removal and the post-transfer reconnect state separately. Read-only model settings show the pause; cached translations remain available. When the source used the platform provider without BYOK or an existing pause, no reconnect pause is set and the destination's normal plan/quota gates apply. Last WordPress sync origin and key ID are invalidated. |
| Webhooks | Endpoints stay as disabled configuration, but their source-owned signing secret is erased. Pending deliveries are marked failed and past delivery records remain. Enabling an endpoint with no secret requires an explicit reconnect/secret rotation through the existing manager action; transfer does not rotate a live secret. URL safety checks remain in creation/update and dispatch. |
| Notifications | Optional notification preferences and delivery claims belong to the original user/workspace membership and never move. Weekly activity derives its organization/project scope from current membership; historical batches remain attributed to source. |

The transfer row lock is also the boundary for concurrent project writes. A successful authorization check before a request starts does not authorize a later commit after ownership changes.

| Concurrent writer | Commit rule around transfer |
| --- | --- |
| Settings, provider key, language model, translation memory, runtime sync origin and switcher | Re-read manager membership under the project row lock in the write transaction. A former source manager cannot restore a cleared provider key. |
| API key create/revoke | Re-read manager membership under that lock; plugin writes separately recheck that the presented key is still active at commit. The old hashed key cannot be reused in the destination. |
| Languages, slugs, exclusions/CSV, media | Revalidate manager membership and the current language configuration under the row lock. File imports repeat this per chunk, so a transfer between chunks stops subsequent writes. |
| Glossary, translation text, workflow, manual editor, import | Re-read the actor's current access and language scope at commit. Editor capability tokens carry the issuing workspace and user; transfer invalidates existing editor sessions. Manual content already committed remains with the project. |
| Project members and invitations | Re-read current manager membership before updating roles/invitations. Source-only members and pending invitations are removed by transfer. Invitations and email delivery have a separate external side-effect boundary. |
| Webhook endpoint/test/delivery | Manager writes use the project lock; transfer disables endpoints, erases secrets and fails pending deliveries. Delivery HTTP already underway has an external side-effect boundary and must not hold the project row lock across the request. |
| Plugin settings sync, page-view events, translation, batch usage | Old API keys are rejected after transfer. Settings sync and page-view persistence recheck the active key under the project lock. Historical billed usage and batch logs retain the source organization; new destination usage requires a newly connected key. |
| URL operations and WordPress URL sync | Manager claim, delete and crash recovery re-read current management rights under Organization→Project locks. Provider dispatch and billed persistence repeat that check. WordPress URL sync rechecks the active API key under the same lock. Source-org receipts cannot be recovered after a move; a new URL operation uses a new destination-scoped idempotency namespace. |

An external paid provider request can start before transfer and finish after it. The database guard rejects its stale source-workspace usage/batch write and rolls back the local translation transaction. This does **not** undo a provider-side cost. Such a rejected request must be diagnosed from provider/request evidence; it is neither automatically replayed nor reported as zero external spend. Do not hold a database row lock across the provider HTTP call. Operators should quiesce plugin traffic before a planned transfer where exact cost reconciliation is required.

The source may still need accounting access to historical billed rows. A destination manager can see project-scoped content after transfer but receives no source subscription, member list or credentials. A source user without destination access loses access to the moved project. Both SaaS and WordPress runtime configuration should be checked after the new plugin key is installed. The transfer does not itself mutate a customer WordPress site or call a paid translation provider.

Apply `scripts/sql/workspace-transfer.sql` to each target database after the #263 URL operations migration and before deploying this application. This is an **expand** migration: `UrlOperationReceipt.originatingOrganizationId` stays nullable because old #263 instances may continue creating receipts while the new deployment builds and rolls out. New #267 writers always store the real billed organization in the receipt/usage transaction; recovery refuses a NULL origin. A project with any NULL receipt cannot be transferred until original billing evidence resolves it. Count receipts and pending operations before migration and after deployment, but do not infer or fabricate a backfill from current project ownership. A NOT NULL contraction needs separate evidence that no old writers remain and every historical receipt is correctly attributed; it is not part of this release. Use isolated fixture projects for Preview and Production verification; do not move a customer project as a smoke test. Verify the audit row, retained historical attribution, invalidated credentials and fresh destination runtime readback, then remove the fixture.
