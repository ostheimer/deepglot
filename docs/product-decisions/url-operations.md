# Operational translated URLs

The SaaS URL inventory accepts manager-only actions. `POST /api/projects/{projektId}/url-operations` with `{ action, id }` returns a fresh side-effect-free preview. Submit the returned `confirmation` with an `Idempotency-Key` equal to that token to execute it. A changed URL, segment, context, project language, provider setting or quota limit invalidates the preview. Monthly usage is rechecked at execution, but is excluded from the content token so the first confirmed URL in a selection does not invalidate later URLs. The selection preview displays the aggregate billable words, while each URL reports its own result and bills at most its confirmed words. Replaying the same confirmation returns the original response without repeating provider work.

Each URL step is bounded to 250 eligible segments. The preview shows the complete eligible count and the number remaining; successful results with `nextAfterId` can be followed by a new preview with `afterId`, then a separate confirmation. The persistence receipt stores this cursor and remaining count so a lost response can be recovered without losing the approved batch's progress. This also keeps a larger URL record until its last delete step. A delete cursor cannot skip still-eligible earlier segments. The inventory query is capped at 10,000 associated segments; larger records receive an explicit error and require a narrower inventory before mutation. The browser handles up to ten selected URLs sequentially and reports partial results, including quota failures, per URL.

Retranslation means re-generating *existing* machine segments uniquely associated with one observed source URL path and target language. It does not crawl the live site, discover new text, or guarantee that a WordPress page cache immediately reflects the new SaaS values. A fresh translation is billed through the normal translation API, including its quota, velocity, language, automatic-translation, provider and persistence guards. The preview gives the exact number of source words to be billed on successful persistence and the current organization monthly usage and effective limit. Provider charges can occur even when later persistence fails; in that case the velocity reservation is retained as in normal translation. Manual, reviewed, currently glossary-protected and observed shared segments are skipped, and approved organization translation memory cannot turn a forced refresh into a free cache hit.

Before calling a provider the URL is atomically marked `provider_pending` with its confirmation token in `operationToken`. Concurrent confirmations and recovered idempotency leases cannot start another paid attempt for that URL. Only a response produced before provider dispatch is automatically recorded as retryable. A successful persistence writes a `UrlOperationReceipt` in the same transaction as billed usage; it binds the manifest token to the project, URL, target language, path and managing actor. Replay checks those identities and current manager membership before reconciling a crash after that transaction without another provider call. Any error after dispatch without this receipt, including a 4xx response, remains pending and blocks both new retranslation and deletion. Unknown provider costs are not reported as zero; `billedWords` is returned only for proven SaaS usage or a pre-provider rejection. The idempotency response replay alone does not guarantee exactly-once provider billing after a crash.

For an unresolved pending URL, the operator must capture the project ID, URL ID and `operationToken`, then inspect `UrlOperationReceipt.id = operationToken`, the current translation versions, UsageRecord/TranslationBatchLog entries for that attempt window and the provider's request or billing record. If a receipt exists, replay the same confirmed request; it completes from the receipt without a provider call. If no receipt exists, document whether the provider accepted/billed the attempt and whether any local persistence happened. Only after that evidence is recorded may a database operator reset exactly the matching row in a transaction: `UPDATE "TranslatedUrl" SET "operationState" = 'failed', "lastResult" = 'operator_reconciled', "lastError" = 'operator_reconciled', "lastOperationAt" = NOW() WHERE "id" = :url_id AND "projectId" = :project_id AND "operationState" = 'provider_pending' AND "operationToken" = :confirmation;` Check that precisely one row changed. A new manager preview is then required; any additional provider charge must be presented and approved again. An HTTP status by itself is never proof of non-billing.

Deletion permanently removes the selected URL inventory record, exclusive unreviewed machine translations and this path's context links. Shared translation data, manual and reviewed translations, other URL and language records, historical `UsageRecord` and `TranslationBatchLog` rows remain. A project runtime lock and row/content checks serialize deletion with translation persistence and reject stale context changes. Glossary create/update/delete paths use that same lock; both deletion and forced translation recheck the current rule revision inside their transaction before changing a segment or booking usage. A subsequent real request can create the URL and its cache again. Both successful retranslation and deletion append digest-only `UrlCacheInvalidation` events in their persistence transaction. The WordPress plugin reads a bounded cursor feed with its regular runtime refresh and deletes only the corresponding current and legacy translation transients. A failed deletion leaves the cursor unchanged so the event is retried. WordPress full-page caches and upstream CDNs are independent; operators must rebuild and verify them separately.

Only actual new dashboard actions or bounded WordPress sync attempts populate operation state, result, HTTP code and origin. Previous `lastSeenAt` analytics do not establish HTTP success or provenance. The plugin reports completed/failed/retrying attempts to `POST /api/plugin/url-sync-result` using its existing API key, with a bounded HTTP request. Reports are accepted only for an active project language and same-site URL. A failed report does not stop the WordPress job; its authoritative local job status remains available in WordPress admin. The dashboard error report filters recorded failures and opens the existing WordPress bounded retry workflow. No permanent crawler or cross-site fetch is added.

Apply the additive, repeatable `scripts/sql/url-operations.sql` to each target database before deploying a Prisma client that reads these columns. Verify it first on an isolated clone, then Preview and Production in release order. Do not infer deployment or public WordPress acceptance from a passing local test or Preview READY state.
